# TM PostgreSQL Stored Procedure and Function Validator

Java 21 and Spring Boot application that discovers PostgreSQL functions and procedures in `public` on every startup. It executes only routines whose behavior and write scope pass conservative static and metadata checks. Write test cases are committed independently only after row-level verification; reads run in read-only transactions. The validator does not create or alter database objects.

## Safety and validation behavior

- Discovery queries `pg_catalog.pg_proc` joined to `pg_catalog.pg_namespace`, selects the configured schema, and preserves overloads by OID and identity signature. It includes functions and procedures with `IN`, `OUT`, and `INOUT` metadata; window functions are discovered and reported as blocked because they need an `OVER` invocation context.
- Behavior is classified only as `READ` or `WRITE` from routine source, catalog dependencies, and referenced tables. Any recognized write makes the classification `WRITE`, including routines that also read. Behavior that cannot be resolved is conservatively classified as `WRITE` and blocked with a reason. Dynamic SQL, unresolved or overloaded calls, unsupported languages, privileged routines, unsafe session/sequence/external operations, and routines with unbounded effects are blocked with a reason.
- Write targets must have primary keys, row-level security disabled, and no user triggers or rewrite rules, including on partitions. Row snapshots are bounded by the configured limits. Updates and deletes require every primary-key predicate input to resolve to a record generated by the current run. Deletes are blocked when inbound foreign keys could cause dependent row effects.
- Foreign-key values reuse the first existing valid reference, then a current-run generated parent record. Composite references are selected as one coherent row. Missing required parents are reported; the validator never writes prerequisite rows directly.
- Values use PostgreSQL type, nullability, identity, default, unique, foreign-key, and simple check-constraint metadata. Explicit identity or sequence-backed insert inputs are blocked to avoid bypassing their generators. Unsupported types or check expressions are blocked rather than guessed. One input set is generated per case by default; nullable inputs and database defaults add bounded variants.
- Procedures that manage transactions internally are invoked outside Spring-managed transactions only in `AUTOCOMMIT_BOUNDED` mode and only after the same bounded-target checks. Their effects cannot be rolled back by the validator; this limitation is recorded.
- Normal writes are committed only after both the returned result shape and bounded row changes are verified. PostgreSQL sequence values may still advance when a failed write rolls back; sequence advancement is not transactional.
- Default expressions that call an unreviewed function block writes before invocation. Known PostgreSQL generators and pure built-ins are allowed, while custom default functions require review outside automatic testing.
- A session advisory lock prevents duplicate runs across application instances. Each test case checkpoints the run report. Reports use atomic replacement and contain hashes or redacted markers instead of stored business row values. SQL exception details are omitted while SQLSTATE is retained.

The application is intentionally capable of committing verified test data through eligible routines because the requested workflow requires persistent independent writes. Review `reports/run-<run-id>.json` after each startup. `validator.max-routines` is an execution guard: discovery still classifies every routine, but if the discovered count exceeds the configured limit, all routines are blocked before invocation. Set `VALIDATOR_STARTUP_ENABLED=false` to start without running the validator during maintenance.

## External database configuration

Set `TM_DB_URL`, `TM_DB_USERNAME`, and `TM_DB_PASSWORD` outside the project. The default URL targets `jdbc:postgresql://localhost:5432/tm`; no username or password is embedded. Use a restricted PostgreSQL account that can read metadata, execute only the routines you intend to validate, and inspect the target rows.

All `validator.*` properties can be overridden with Spring environment variables. For example, `VALIDATOR_MAX_TESTS_PER_RUN`, `VALIDATOR_MAX_GENERATED_ROWS_PER_RUN`, `VALIDATOR_MAX_SNAPSHOT_ROWS_PER_TABLE`, `VALIDATOR_RUN_TIMEOUT_SECONDS`, and `VALIDATOR_INTERNAL_TRANSACTION_MODE`.

## Build and run in Windows PowerShell

From `C:\Users\PC\OneDrive\Desktop\TM-Stroedprocedure`:

```powershell
$env:TM_DB_URL = 'jdbc:postgresql://localhost:5432/tm'
$env:TM_DB_USERNAME = 'your-database-user'
$securePassword = Read-Host 'PostgreSQL password' -AsSecureString
$env:TM_DB_PASSWORD = [System.Net.NetworkCredential]::new('', $securePassword).Password
Remove-Variable securePassword

.\mvnw.cmd clean verify
.\mvnw.cmd spring-boot:run
```

The Spring Boot Maven plugin runs the startup validator. To package and run the executable jar:

```powershell
.\mvnw.cmd package
java -jar .\target\tm-stored-procedure-validator-1.0.0-SNAPSHOT.jar
```

List recent reports and inspect the latest run summary without printing generated-input details:

```powershell
Get-ChildItem .\reports\run-*.json | Sort-Object LastWriteTime -Descending | Select-Object -First 10 Name,Length,LastWriteTime
$latestReport = Get-ChildItem .\reports\run-*.json | Sort-Object LastWriteTime -Descending | Select-Object -First 1
$report = Get-Content -LiteralPath $latestReport.FullName -Raw | ConvertFrom-Json
$report | Select-Object runId,startedAt,completedAt,database,schema,status,discoveredRoutines,attemptedCases,verifiedCases,committedWrites,failedCases,blockedRoutines,skippedCases
```

## Testing

`mvnw.cmd clean verify` runs unit tests only. Unit tests do not connect to the configured `tm` database or invoke stored routines. Live metadata and routine behavior remain unverified until the application is intentionally started with the external database variables configured.
